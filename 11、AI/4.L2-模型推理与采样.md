# L2：模型的“调用”与“控制”——推理与采样

> 对应《1.全流程.md》第二层。**模型参数一动不动**，你只是在调整“读取方式”。
> 学习目标：搞懂你花钱调 API 时，那些参数（Temperature/Top-P…）到底在控制什么，以及如何省 Token、防幻觉。

---

## 一、推理（Inference）：模型“干活”的过程

### 1.1 在做什么
把训练好的模型“跑起来”：输入你的 Prompt，模型执行**前向传播**，**逐字（逐 Token）预测下一个词的概率**，再按某种规则选词，循环直到结束。

> 注意：推理时**权重完全不变**。同一个模型，不同人调出不同效果，靠的全是 L2 这一层的参数和提示。

### 1.2 两个阶段：Prefill 与 Decode ⭐

这是理解“为什么首字慢、后续快”和推理成本的关键。

| 阶段 | 做什么 | 特点 |
| :--- | :--- | :--- |
| **Prefill（预填充）** | 一次性并行处理你输入的整个 Prompt | 计算密集，决定 **TTFT（首字延迟）** |
| **Decode（解码）** | 一个一个 Token 地生成输出 | 串行，逐字蹦，决定后续生成速度 |

*   **输入越长 → Prefill 越久 → 首字越慢**。
*   输出是串行的，所以**长输出天然比长输入慢**。

### 1.3 KV Cache（键值缓存）⭐
生成第 N 个词时，需要用到前面所有词的 K、V（见 L0 Attention）。如果每次都重算，巨慢。
*   **KV Cache** 把已经算过的 K、V **缓存**起来，生成新词时直接复用，只算新词的部分。
*   **代价**：缓存占显存，且**上下文越长，KV Cache 越大**——这是长上下文“费显存”的主因（L4 的 vLLM PagedAttention 就是优化它）。

> ⚠️ **别混淆：KV Cache“看前文” ≠ 自回归生成（Autoregressive Generation）**
> *   **自回归**是更上层的**循环框架**：生成一个字 → 把它接到序列末尾当作新输入 → 再生成下一个字……即“**用自己刚生成的输出当作下一步的输入**”。（佐证：RNN/LSTM 也是自回归，但根本没有 Attention。）
> *   **Attention + KV Cache** 则是这个循环**每一步内部**“高效看前文”的具体实现。
> *   一句话：**自回归回答“为什么一个一个生成”，Attention/KV Cache 回答“每生成一个时怎么高效地看前文”**——两者协作，但不是同一个概念。

## 二、采样策略（Sampling）：控制“选哪个字” ⭐

模型每一步会输出一个**概率分布**（词表里每个词的概率）。“选哪个”就是采样策略，它直接决定输出的**随机性与风格**。

### 2.1 最朴素的两种
*   **贪心解码（Greedy）**：每步都选概率最高的词。结果稳定但呆板，容易复读。
*   **Beam Search（束搜索）**：同时保留多条候选路径，最后选整体概率最高的。常用于翻译/摘要，但对开放生成偏“安全无聊”。

### 2.2 Temperature（温度）—— “胆量旋钮”
调整概率分布的“陡峭程度”：
*   **低（0~0.3）**：分布变陡，几乎只选最稳妥的词 → 确定、严谨。**适合代码、数学、客服、抽取**。
*   **高（0.8~1.2）**：分布变平，敢选低概率的生僻词 → 多样、有创意。**适合写诗、头脑风暴、起名**。
*   `Temperature = 0`：等价于贪心解码（最确定）。

### 2.3 Top-K —— “候选人数量锁”
只在**概率最高的前 K 个**词里随机选。比如 K=50，就只从前 50 个候选里抽。缺点：K 固定，不够灵活（有时该多有时该少）。

### 2.4 Top-P（核采样，Nucleus Sampling）—— “动态候选池” ⭐
按概率从高到低累加，加到累计概率达到 **P（如 0.9）** 就停，只在这个“动态圈”里抽。
*   模型很确定时圈子小（候选少），不确定时圈子大（候选多）—— **自适应**，工业界首选。

### 2.5 三者怎么配合（实战经验）
*   **要稳/严谨**（客服、代码、抽取 JSON）：`Temperature=0~0.3`，`Top-P=0.9`。
*   **要创意**（文案、脑暴）：`Temperature=0.8~1.0`，`Top-P=0.95`。
*   一般 **Temperature 和 Top-P 调一个就好**，别两个都拉满。

### 2.6 惩罚项（抑制复读机）
*   **Frequency Penalty（频率惩罚）**：一个词出现越多次，越压低它再出现的概率。
*   **Presence Penalty（存在惩罚）**：只要出现过就压一下，鼓励聊新话题。
*   用来治“车轱辘话来回说”的复读现象。

### 2.7 其他常用生成参数
*   **Max Tokens**：最多生成多少 Token（控制长度和成本）。
*   **Stop Sequences（停止词）**：遇到指定字符串就停止生成。
*   **Logprobs**：返回每个 Token 的概率，可用于做置信度分析。
*   **Seed**：固定随机种子，让结果可复现。

## 三、提示工程（Prompt Engineering）：性价比最高的技能 ⭐

不改一行模型，靠“怎么问”就能大幅提升效果。

### 3.1 System Prompt vs User Prompt
*   **System Prompt（系统提示）**：设定角色、规则、边界、语气。“你是携程的专业客服，只回答酒店相关问题，禁止…”。
*   **User Prompt（用户提示）**：用户的具体问题。
*   好的系统提示是产品“人设”和“护栏”的第一道防线。

### 3.2 Zero-shot / Few-shot
*   **Zero-shot（零样本）**：直接问，不给例子。
*   **Few-shot（少样本）**：在 Prompt 里给几个“输入→输出”示范，模型照葫芦画瓢。**对格式要求严格、任务特殊时极有效**（利用了 L0 提到的 In-Context Learning 能力）。

```
示例（Few-shot 抽取情感）：
输入: 这家酒店太棒了 → 输出: 正面
输入: 房间又脏又吵   → 输出: 负面
输入: 服务一般般     → 输出:    ← 让模型补全
```

### 3.3 CoT（Chain of Thought，思维链）⭐
让模型**“一步步思考”再给答案**，显著提升推理/数学/逻辑题正确率。
*   最简单的触发：在提示里加一句 **“Let's think step by step / 请一步步推理”**。
*   进阶：**Few-shot CoT**（给带推理过程的示例）、**Self-Consistency**（生成多条推理路径投票选最一致的答案）。
*   现代“推理模型”（如 o1、DeepSeek-R1）本质是把 CoT 内化进了训练，自动长思考。

### 3.4 结构化输出（Structured Output / JSON Mode）⭐
让模型严格按固定格式（如 JSON）返回，方便程序解析，是做 Agent / 工程化的刚需。
*   手段：JSON Mode、Function Calling（见 L3）、约束解码（Grammar/Outlines）、提供 Schema。
*   配合 `Temperature=0` 提升稳定性。

### 3.5 其他实用技巧
*   **角色扮演**、**分隔符**（用 ``` 或 XML 标签框住内容防混淆）、**先给指令再给数据**、**让它先复述要求**等。

## 四、上下文窗口（Context Window）⭐

*   **定义**：模型一次能“看到”的最大 Token 数（输入 + 输出共享）。如 128K = 12.8 万 Token。
*   **超了会怎样**：超出部分被截断，模型“忘记前文”——这是为什么要 **RAG（L3）** 来按需喂资料，而不是把全部资料塞进去。
*   **“Lost in the Middle”现象** ⭐：即使在窗口内，模型对**放在中间**的信息也容易忽略，**开头和结尾**的信息最受重视。所以：
    *   把最重要的指令/资料放在**开头或结尾**。
    *   不要无脑塞满上下文，**相关性 > 数量**。
*   **长上下文的代价**：更慢（Prefill 久）、更贵（Token 多）、更占显存（KV Cache 大）。

## 五、幻觉（Hallucination）与对抗

### 5.1 什么是幻觉
模型**一本正经地编造事实**：捏造不存在的论文、API、法条、数字。

### 5.2 为什么会发生
*   模型本质是“预测最像样的下一个词”，它追求**“流畅合理”而非“真实”**。
*   知识有**截止日期**，问它训练后的事它只能瞎编。
*   Temperature 太高、资料不足时更严重。

### 5.3 怎么对抗
*   **降低 Temperature**（严谨场景调到 0~0.3）。
*   **Grounding（事实锚定）/ RAG**：把权威资料喂给它，让它“开卷答题”并要求**引用来源**（见 L3）。
*   **提示约束**：明确告诉它“不知道就说不知道，不要编”。
*   **后置校验**：用规则/另一个模型核对关键事实。

## 六、Token 经济学：怎么算钱、怎么省

### 6.1 计费方式
*   按 Token 计费，**输入 Token 和输出 Token 通常分别定价**（输出往往更贵）。
*   总成本 ≈ `输入Token数 × 输入单价 + 输出Token数 × 输出单价`。
*   多轮对话里，**历史会被反复带入**，Token 会滚雪球——这是聊天应用成本的隐形大头。

### 6.2 省 Token 的常见手段
*   **精简 Prompt**：去废话、压缩系统提示。
*   **截断/摘要历史**：长对话定期总结，不要全量带入。
*   **RAG 只喂相关片段**，别塞整篇文档。
*   **缓存**：Prompt Caching（复用固定前缀）、语义缓存（见 L4）。
*   **模型路由**：简单问题走便宜小模型，难题才上大模型（见 L4）。
*   **限制 Max Tokens**，避免无意义长输出。

> 🛠️ 实操：用 `tiktoken` 预估 Token 数；很多平台支持 **Prompt Caching**，把不变的系统提示/文档前缀缓存起来大幅降价。

## 📌 本章小结
> 推理 = **Prefill（处理输入）+ Decode（逐字生成）**，靠 **KV Cache** 提速。输出风格由**采样策略**控制：**Temperature** 调胆量、**Top-P** 调动态候选池，严谨场景调低、创意场景调高。
> 不改模型、靠 **Prompt 工程（System Prompt / Few-shot / CoT / 结构化输出）** 就能大幅提效。注意**上下文窗口**有限且“中间易遗忘”，警惕**幻觉**（用低温+RAG+引用来治），并时刻算好 **Token 账**。

## 🔬 深挖清单详解（逐条讲透）

> 对应《1.全流程.md》L2 的「深挖清单 ✅」。

### 1）Temperature / Top-K / Top-P 三者如何配合调
*   **执行顺序**：模型先出概率分布 →（Temperature 缩放分布）→（Top-K 砍候选）→（Top-P 再砍候选）→ 在剩下的里随机抽。
*   **配合原则**：**通常只主调一个**，别全开。
    *   要确定/严谨：`Temperature=0`（直接贪心，Top-K/P 失效）。
    *   要平衡：`Temperature=0.7` + `Top-P=0.9`（最常用组合）。
    *   要发散：`Temperature=1.0` + `Top-P=0.95`。
*   **场景速查**：代码/抽取/客服→低温；问答/总结→中温；文案/脑暴→高温。

### 2）CoT、Few-shot 的实战写法
**Few-shot（给范例）**：
```
请判断情感（正面/负面/中性）：
评论：房间很干净 → 正面
评论：等了一小时还没上菜 → 负面
评论：位置一般 → 中性
评论：前台服务很热情 →
```
**Zero-shot CoT（一句话触发思考）**：
```
小明有 5 个苹果，给了小红 2 个，又买了 3 箱每箱 6 个，现在有几个？
请一步步推理，最后用“答案：”给出结果。
```
**Few-shot CoT（给带推理过程的范例）**：在示例里把“怎么想出来的”也写出来，模型会模仿这种推理链。
> 经验：复杂推理/数学务必加 CoT；格式要求严格用 Few-shot 给样例最稳。

### 3）KV Cache 与 Prefill/Decode 的关系
*   **Prefill 阶段**：并行处理整个输入 Prompt，顺便把每个 Token 的 K、V **算好存进 Cache**。
*   **Decode 阶段**：生成每个新词时，只需算新词的 Q，再去 **复用 Cache 里全部历史 K、V** 做 Attention，无需重算前文。
*   **所以**：没有 KV Cache，每生成一个字都要把前文重算一遍（O(n²) 爆炸）；有了它，Decode 变得高效。代价是 **Cache 占显存，且随上下文线性增长**（vLLM 的 PagedAttention 就是优化它，见 L4）。

### 4）上下文窗口与“Lost in the Middle”
*   **上下文窗口**：输入+输出 Token 总上限，超出即截断/遗忘。
*   **Lost in the Middle**：实验发现模型对**开头和结尾**的信息利用最好，**放中间的关键信息容易被忽略**。
*   **实操对策**：① 把最重要的指令/证据放在 Prompt **开头或结尾**；② RAG 检索结果**按相关性把最相关的放首尾**；③ 别贪多塞满，**相关性 > 数量**；④ 超长任务先摘要压缩。

### 5）如何让模型稳定输出 JSON（约束解码）
从弱到强四种手段：
1.  **提示约束**：明确“只输出 JSON，不要任何多余文字”，并给 Schema 示例。
2.  **JSON Mode**：很多 API 有开关，强制输出合法 JSON。
3.  **Function Calling / Tool**：让模型按工具参数 Schema 返回结构化数据（最常用，见 L3）。
4.  **约束/语法解码（Grammar）**：用 Outlines、JSON Schema 约束，在解码层面**只允许生成符合格式的 Token**，100% 合法。
> 再配 `Temperature=0` 提升稳定性。务实组合：**Function Calling + 低温**。

### 6）Token 经济学：怎么算 Prompt 成本、怎么省 Token
*   **算账**：`成本 = 输入Token×输入单价 + 输出Token×输出单价`（输出通常更贵）。多轮对话历史会**累计带入**，是隐形大头。
*   **省钱清单**：
    *   精简系统提示、删冗余示例。
    *   长对话**定期摘要**代替全量历史。
    *   RAG **只塞最相关片段**，不塞整篇。
    *   **Prompt Caching**：缓存固定前缀（系统提示/长文档），命中大幅降价。
    *   **语义缓存**：相似问题直接复用答案（见 L4）。
    *   **模型路由**：简单问题走便宜小模型。
    *   设 `max_tokens` 防超长输出。
> 用 `tiktoken` 先把 Prompt Token 数估出来，再针对性瘦身。
