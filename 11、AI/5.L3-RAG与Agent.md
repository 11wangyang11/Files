# L3：模型的“四肢”与“外挂”——RAG 与 Agent

> 对应《1.全流程.md》第三层。让 AI 能查实时资料、能记住事、能干具体活。
> 学习目标：搞懂 RAG 全链路 + Agent 工作原理，这是“业务落地”的核心技术层。

> 🏷️ **流派归属**：本章是 **🔵 Encoder + 🟢 Decoder 拼接最典型的地方**——RAG 检索侧（Embedding / Rerank）走 Encoder-Only（L0 §4.6）；生成回答和 Agent 推理走 Decoder-Only（L0 §4.5 + L2）。对照表与 RAG 交接图见 [1.全流程.md §三大流派×五层](./1.全流程.md)。

---

## 为什么需要这一层

光靠模型自己（L0~L2）有三个天然短板：
1.  **知识冻结**：训练完知识就定格了，不知道最新/私有信息。
2.  **会幻觉**：不知道也硬编。
3.  **只会说不会做**：不能查数据库、发邮件、下订单。

> **RAG** 解决前两个（给它“查资料的眼睛”）；**Agent + Tool** 解决第三个（给它“干活的手脚”）。

# 第一部分：RAG（检索增强生成）

## 一、一句话理解
**开卷考试**：先从外部知识库**检索**出相关资料，再把资料连同问题一起塞进 Prompt，让模型**基于资料**回答。

```
用户提问 ─▶ 检索知识库 ─▶ 取出相关片段 ─▶ 拼进 Prompt ─▶ 模型基于资料作答(并引用来源)
```

好处：知识可实时更新、答案可溯源、大幅减少幻觉，且**不用重新训练模型**。

---

## 二、RAG 完整链路（每一环都是坑）

RAG 分**离线建库**和**在线问答**两大阶段。

### 阶段 A：离线建库（Indexing）
```
原始文档 → 清洗 → Chunking分块 → Embedding向量化 → 存入向量数据库
```

#### 1. 文档清洗
去页眉页脚、广告、乱码；处理表格、图片；**粘合跨页被切断的段落**。垃圾进、垃圾出，清洗质量决定上限。

#### 2. Chunking（分块）⭐ —— RAG 第一大坑
把长文档切成小块（Chunk），因为：① 上下文窗口有限；② 检索粒度要适中。

常见策略：
| 策略 | 说明 | 适用 |
| :--- | :--- | :--- |
| **固定长度分块** | 按字数/Token 切，带 **overlap 重叠**防切断语义 | 简单通用 |
| **按语义/结构分块** | 按段落、标题、Markdown 层级切 | 结构化文档 |
| **父子分块（Small-to-Big）** | 用小块检索（精准），返回所在大块（上下文全） | ✅ 进阶常用 |

关键参数：**chunk_size（块大小）** 和 **chunk_overlap（重叠量）**。太大噪声多、太小丢上下文，需实验调优。

#### 3. Embedding（向量化）⭐
用 **Embedding 模型**（如 bge、m3e、text-embedding-3）把每个文本块变成一串数字向量。
*   **核心性质**：**语义相近的文本，向量距离也近**。“怎么退款”和“退货流程”虽用词不同，但向量靠得近。
*   选模型看：语种支持、维度、检索效果（MTEB 榜单）、是否支持长文本。

#### 4. 向量数据库（Vector DB）
存储向量并支持**高速相似度检索**（用 ANN 近似最近邻算法，如 HNSW）。
*   常见：**Milvus、Qdrant、Weaviate、pgvector、Chroma、Faiss（库）**。

### 阶段 B：在线问答（Retrieval + Generation）
```
用户问题 → 向量化 → 检索Top-K → Rerank精排 → 拼Prompt → 模型生成
```

#### 5. 检索（Retrieval）⭐
*   **向量检索（语义检索）**：把问题也向量化，找最近的块。**懂语义**，但对专有名词/编号不敏感。
*   **关键词检索（BM25/全文）**：传统倒排索引，**精确匹配**词，擅长术语、型号、人名。
*   **混合检索（Hybrid Search）** ⭐：两者结合（再融合排序，如 RRF），**召回又全又准**，工业界推荐。

#### 6. Rerank（重排序）⭐ —— 提准的关键一步
初筛（如 Top-100）速度快但不够准。再用 **Rerank 模型（Cross-Encoder，如 bge-reranker、cohere-rerank）** 对问题和每个候选**一对一精算相关性**，重新排序，选出最相关的 Top-3。
*   **为什么需要**：检索的 Embedding 是“分别编码”，Rerank 是“成对深读”，精度高得多。
*   代价：慢，所以只对初筛少量结果做。

#### 7. 生成（Generation）
把 Top-N 资料 + 问题拼成 Prompt（配 `Temperature=0.3`），要求模型**只依据资料作答并标注来源**。→ 🟢 **Decoder-Only**（L0 §4.5 + L2 采样控制）

---

## 三、RAG 进阶玩法
*   **Query 改写/扩展**：把口语化问题改写得更利于检索；HyDE（先让模型假设一个答案再用它去检索）。
*   **GraphRAG（知识图谱增强）**：把知识构建成实体关系图，擅长回答需要“多跳推理/全局总结”的问题。
*   **Agentic RAG**：让 Agent 自主决定“要不要检索、检索什么、检索几次”，而非固定流程。
*   **多路召回 + 融合**：向量、关键词、图谱多路并行再融合。

# 第二部分：Agent（智能体）

## 四、一句话理解
**会自己动脑、动手的 AI**。不只“回答问题”，还能**规划步骤、调用工具、观察结果、循环推进**，直到完成目标。

> 例：“帮我订明天去北京最便宜的机票”→ Agent 自己规划：查日期 → 调机票接口比价 → 选最便宜 → 调支付 → 反馈结果。

---

## 五、Agent 核心范式：ReAct ⭐

**ReAct = Reasoning（推理）+ Acting（行动）** 交替循环，是 Agent 的经典骨架：

```
Thought（想）：我需要先查一下用户的订单状态
Action（做）：调用 query_order(order_id="123")
Observation（看）：返回 {status: "已发货"}
Thought（想）：已拿到状态，可以回答了
Answer（答）：您的订单已发货...
```

模型每一轮输出“思考 + 要调的工具”，系统执行工具把结果喂回去，循环往复——**想一步、做一步、看结果、再想下一步**。

---

## 六、Agent 的关键能力

### 6.1 规划（Planning）
把大任务拆成子任务。手段：任务分解、**ReAct**、**Plan-and-Execute**（先列完整计划再逐步执行）、ToT（思维树）。

### 6.2 反思（Reflection）
做完后**自我检查、发现错误、再纠正**（如 Reflexion）。让 Agent 不是一锤子买卖。

### 6.3 记忆（Memory）⭐
*   **短期记忆**：当前对话上下文（受上下文窗口限制）。
*   **长期记忆**：把历史对话/知识**存进向量库**，需要时检索回来（本质是给 Agent 用 RAG 做记忆）。
*   工程上还分：工作记忆、情景记忆、用户画像记忆等。

### 6.4 工具使用（Tool Use）—— 见下一节

---

## 七、Tool / Function Calling ⭐

Agent 的“手脚”。模型本身不能查天气、发邮件，但能**输出“我要调用哪个函数、传什么参数”**，由外部程序实际执行。

### 工作流程
1.  你把可用工具的 **Schema（名称、功能、参数定义）** 告诉模型。
2.  模型判断需要时，返回结构化调用，如：
    ```json
    { "name": "get_weather", "arguments": { "city": "北京" } }
    ```
3.  你的程序真正执行该函数，把结果返回给模型。
4.  模型基于结果继续推理/回答。

> 这就是 L2 “结构化输出”能力的直接应用。工具描述写得好不好，直接决定模型会不会、用得对不对。

---

## 八、MCP（Model Context Protocol，模型上下文协议）⭐

*   **类比**：**工具调用界的 USB-C 接口 / Type-C 标准**。
*   **解决的痛点**：以前每个应用要接每个工具（查天气、订酒店、连数据库）都得各写一套适配代码，N×M 的对接地狱。
*   **MCP 怎么做**：定义统一协议标准。工具方按标准做成 **MCP Server**，Agent 端作为 **MCP Client**，就能**即插即用**地挂载任意符合标准的工具/数据源。
*   **价值**：生态复用——一次实现的 MCP Server，任何支持 MCP 的客户端（Claude、Cursor 等）都能用。

---

## 九、Skill（技能）

*   在 Agent 框架里，**Skill 通常指为完成特定任务封装好的业务级操作单元**（如“发送企业微信消息”“生成报表”）。
*   它**底层依赖 Tool**，但更偏业务、更高层、更可复用，常带有自己的提示词/流程。
*   类比：Tool 是“底层 API”，Skill 是“面向业务打包好的功能模块”。

---

## 十、编排框架（Orchestration）

把上面所有零件“串起来”的工具：

| 框架 | 定位 |
| :--- | :--- |
| **LangChain** | 最流行的“积木库”，封装 LLM 调用、Prompt、Chain、工具、RAG 等 |
| **LlamaIndex** | 专注 RAG/数据索引，建库检索很强 |
| **LangGraph** ⭐ | 用**图/状态机**编排复杂的、带循环和分支的 Agent 流程 |
| **其他** | AutoGen、CrewAI（多智能体）、Dify/Coze（低代码平台） |

### LangGraph 为什么重要
真实 Agent 流程有**循环、分支、条件、人工介入**，简单的线性 Chain 表达不了。LangGraph 把流程建模成**节点（Node）+ 边（Edge）+ 共享状态（State）** 的图，天然适合 ReAct 这种循环。（客服落地常用，详见 L4 实战）

---

## 十一、Workflow vs Agent：关键的工程抉择 ⭐

| | Workflow（工作流） | Agent（智能体） |
| :--- | :--- | :--- |
| 路径 | **人为固定**好的步骤 | 模型**自主决策**下一步 |
| 可控性 | 高、可预测 | 低、可能跑偏 |
| 成本 | 低 | 高（多轮调用） |
| 适用 | 流程明确的任务 | 开放、需灵活应变的任务 |

> 🔑 实践箴言（Anthropic 也强调）：**能用 Workflow 解决就别上 Agent**。先用固定流程 + 工具，只有当任务确实需要动态决策时，才引入 Agent 的自主性。

---

## 十二、多智能体（Multi-Agent）

多个各有分工的 Agent 协作完成复杂任务：
*   **典型角色分工**：规划者（Planner）+ 执行者（Executor）+ 审查者（Critic）。
*   **协作模式**：主管-下属（Supervisor）、流水线、辩论、群聊。
*   **优点**：分而治之、各司其职、可并行。
*   **缺点**：更贵、更慢、更难调试，沟通开销大。**非必要不上多智能体。**

---

## 📌 本章小结
> **RAG** 给模型装“查资料的眼睛”：清洗 → **分块** → **Embedding** → 存**向量库** → **混合检索** → **Rerank 精排** → 喂模型作答，专治知识过时和幻觉。
> **Agent** 给模型装“干活的手脚”：用 **ReAct（想-做-看循环）** 驱动，靠 **Planning/Reflection/Memory** 增强，通过 **Function Calling / MCP / Skill** 调用外部能力，用 **LangGraph** 编排。工程上牢记：**能 Workflow 就别 Agent，能单 Agent 就别多 Agent。**

## 🔬 深挖清单详解（逐条讲透）

> 对应《1.全流程.md》L3 的「深挖清单 ✅」。

### 1）Chunking 分块策略对比（固定 / 语义 / 父子分块）
| 策略 | 怎么切 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| **固定长度** | 每 N 个 Token 切一刀，带 overlap 重叠 | 简单、可控 | 可能切断句意 |
| **递归/结构** | 按 段落→句子 层级切，或按 Markdown 标题切 | 保语义边界 | 块大小不均 |
| **语义分块** | 用 Embedding 检测“话题转折点”切 | 块内主题集中 | 计算开销大 |
| **父子分块** | 子块（小）做检索，命中后返回父块（大） | 检索精准 + 上下文完整 | 实现稍复杂 |
*   **关键参数**：`chunk_size`（常 256~512 Token）、`chunk_overlap`（常 10~20%）。
*   **经验**：先用“递归分块 + 适当 overlap”做基线，效果不够再上“父子分块”。

### 2）混合检索（向量 + BM25）+ Rerank 的完整 Pipeline
```
用户问题
  ├─▶ 向量检索（语义） ─▶ Top-50
  └─▶ BM25 关键词检索 ─▶ Top-50
         │
         ▼  融合去重（RRF 倒数排名融合）
      候选 Top-100
         │
         ▼  Rerank 模型（Cross-Encoder 成对精算）
      精排 Top-3
         │
         ▼  拼进 Prompt + 引用来源
      模型生成答案
```
*   **向量**懂语义（“退款”≈“退货”），**BM25**抓精确词（型号 `A100`、订单号），**互补**。
*   **RRF**：按各路名次的倒数加权融合，简单稳健。
*   **Rerank**：只对 100 条做（慢但准），把真正最相关的顶上来。

### 3）ReAct 循环的提示词长什么样
```
你可以使用以下工具：
- search(query): 搜索知识库
- query_order(id): 查询订单状态

请按如下格式循环，直到能回答：
Thought: 你的思考
Action: 工具名(参数)
Observation: （系统填入工具返回）
... (可重复多轮) ...
Thought: 我已经知道答案了
Final Answer: 给用户的最终回答

问题：我的订单 A123 到哪了？
```
模型产出 `Thought + Action` → 程序执行工具、把结果写进 `Observation` → 回喂模型 → 循环，直到出 `Final Answer`。

### 4）Agent 的记忆系统怎么设计
*   **短期记忆（对话上下文）**：当前会话消息，受上下文窗口限制 → 过长就**滑动窗口 + 摘要压缩**。
*   **长期记忆**：把历史对话/事实写入**向量库**，需要时按相似度检索回来（本质=给记忆做 RAG）。
*   **结构化记忆**：用户画像、偏好、关键事实存 KV/数据库，精确读取。
*   **写入策略**：不是什么都存，按“重要性/新近度/相关性”筛选与遗忘（类似 Generative Agents 的记忆流）。
> 落地最小方案：短期=最近 N 轮 + 摘要；长期=向量库存“值得记住的结论”。

### 5）Function Calling 的请求/返回数据结构
**① 你声明工具（给模型看的 Schema）**：
```json
{
  "name": "get_weather",
  "description": "查询某城市天气",
  "parameters": {
    "type": "object",
    "properties": { "city": { "type": "string", "description": "城市名" } },
    "required": ["city"]
  }
}
```
**② 模型返回“要调用工具”**：
```json
{ "tool_calls": [ { "name": "get_weather", "arguments": { "city": "北京" } } ] }
```
**③ 你的程序执行后，把结果回传**：
```json
{ "role": "tool", "name": "get_weather", "content": "{\"temp\": 26, \"sky\": \"晴\"}" }
```
**④ 模型基于结果生成自然语言回答**：“北京今天晴，26℃。”
> 描述（description）写得越清楚，模型越知道何时、如何正确调用。

### 6）什么时候用 Workflow、什么时候上 Agent
*   **用 Workflow（固定流程）**：步骤明确、可预测、要稳要省。如“分类→检索→回答”。优先选它。
*   **用 Agent（自主决策）**：任务开放、步骤数不定、需要根据中间结果动态决定下一步。如“帮我调研竞品并出报告”。
*   **判断口诀**：能画出固定流程图就用 Workflow；画不出、必须“边做边定”才上 Agent。
> 业界建议：**从简到繁**——先 Prompt，不够再 Workflow+工具，最后才 Agent，能单 Agent 别多 Agent（成本/可控性考量）。
