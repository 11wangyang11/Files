# Spec 规约驱动开发：在 Cursor 中如何启动与使用

> 配合 [1.全流程.md](./1.全流程.md) L3 的"Spec-Driven Development"一节阅读。
> 本文回答一个核心问题：**spec 不是写几个 markdown 就完事,在 Cursor 里到底怎么"启动并真正生效"?**

---

## 一、先纠正一个最常见的误解

> **spec 的 markdown 文件本身没有任何约束力。** 名字叫 `constitution.md` 还是 `xyz.md` 对 Cursor 毫无区别——Cursor 根本不按这个名字自动加载它。

所以理解 spec 在 Cursor 的关键,是分清两件事:

| 维度 | 含义 | 举例 |
| :--- | :--- | :--- |
| **内容 / 角色（WHAT）** | 这份文档"是什么"、"要什么" | 这是一份"宪法"、一份"需求" |
| **加载通道（HOW）** | Cursor 凭什么把它注入 AI 的上下文 | 放进 `.cursor/rules/`、`@` 引用、命令读取 |

**任何 markdown 都能扮演"宪法/需求"这个角色,但只有走对"加载通道",它才会真正生效。** 名字没有魔力,位置和机制才有。

---

## 二、Cursor 真正"按约定自动加载"的文件

只有这几个是 Cursor 认识、会自动注入上下文的(这才是"有名字魔力"的):

| 位置 / 文件名 | Cursor 行为 | 用途 |
| :--- | :--- | :--- |
| `.cursor/rules/*.mdc` | **自动识别**,按 frontmatter 决定何时注入 | 官方主推,最灵活 |
| `AGENTS.md`（项目根） | **自动加载**进上下文 | 通用 agent 指令文件 |
| `.cursorrules`（项目根） | 自动加载（旧版,已不推荐） | 逐步被 `.cursor/rules/` 取代 |

其他任意位置的 md（如 `spec-demo/constitution.md`）：**Cursor 默认无视**,只有在你 `@` 它、或让 AI 主动读它时才进上下文。

### `.cursor/rules/*.mdc` 的 frontmatter（决定"何时注入"）
```mdc
---
description: 规则用途的简短说明
globs: src/**/*.tsx        # 命中这些文件时才注入（可选）
alwaysApply: true          # true = 每次对话都注入（全局铁律就用它）
---

# 规则正文（markdown）
- 在这里写约束内容……
```

- `alwaysApply: true` → 全局生效（适合"项目宪法"）。
- 只写 `globs` → 编辑匹配文件时才生效（适合"某类文件的局部规范"）。
- 只写 `description` → 由 AI 按需调用（Agent Requested）。

## 三、spec 在 Cursor 的两种用法

### 用法 A：轻量手动流（推荐入门,零安装）

不装任何工具,纯靠"文档 + 对话"就能跑 spec-driven,适合理解本质:

1. **沉淀持久铁律 → 做成 Rule**
   把"技术栈/风格/红线"这类**跨功能、永久生效**的内容,写进 `.cursor/rules/constitution.mdc` 并设 `alwaysApply: true`。这是 spec 的"宪法层",一次配置长期复用。

2. **为本次功能写临时 spec → 普通 md**
   在功能目录下建临时文档(用完归档):
   - `requirements.md`：只写"做什么"(用户故事 + 验收标准,推荐 EARS 句式 `当…时,系统应…`)。
   - `design.md`：让 AI 产出技术方案,**你人工 review**。
   - `tasks.md`：把设计拆成可勾选的小任务。

3. **用一句 prompt 驱动 Agent 逐步执行**
   ```
   请阅读 <功能目录>/requirements.md、design.md、tasks.md，
   严格遵守已生效的项目规则，从 tasks.md 第一条开始实现，
   每完成一条停下来等我验收，通过后再做下一条。
   ```
   > 这句话本身是 **prompt**;被 `@` 或被读取的 spec 文件进入上下文;`alwaysApply` 的 Rule 自动在场。三者配合,才是完整的 spec-driven。

### 用法 B：Spec Kit 工具流（标准化、团队协作）

用 GitHub **Spec Kit** 把流程固化成斜杠命令,适合正式项目:

```bash
# 1. 安装(需要 uv / Python 环境)
uvx --from git+https://github.com/github/spec-kit.git specify init <项目名>

# 2. 在 Cursor 中按顺序执行内置命令(每步自动把对应 spec 读进上下文)
/constitution   # 定全局铁律
/specify        # 写需求(做什么)
/plan           # 出技术方案(怎么做)
/tasks          # 拆任务清单
/implement      # 逐条实现
```

每个命令会自动生成/读取对应文档,**不依赖 AI 自觉去 read**——这正是工具流比手动流更可靠的地方。

> 同类工具:**AWS Kiro**(自带 spec 工作流的 IDE)。理念一致,任选其一。

## 四、spec 本身是"软约束"，硬约束要靠 spec 之外的东西

> ⚠️ 先把最关键的一句说死：**spec 本身永远是软约束（非强约束）。** 它就是文案，不管写得多细，都没有任何机制能强制 AI 照做。**想要强制力，必须在 spec 之外另外加东西。**

很多人误以为 spec 能"约束住"AI——不能。真正能落地的约束力来自三层，但**只有第 1 层才是 spec，第 2、3 层都不是 spec**，而是你额外挂在 spec 旁边的"人"和"程序"：

```
软约束 ───────────────────────────────→ 硬约束
第1层：让文档进上下文        第2层：人工卡点        第3层：机器拦截
（= spec 本体，软）         （= 人，不是 spec）     （= 程序，不是 spec）
```

| 层 | 它是什么 | **是不是 spec？** | 强弱 |
| :--- | :--- | :--- | :--- |
| 第1层 上下文 | spec / rule 这些 markdown | ✅ **就是 spec 本体** | **软**（AI 可以不听） |
| 第2层 人工卡点 | 你 review、逐条验收 | ❌ 是"人"，不是 spec | 中（可靠但累） |
| 第3层 机器拦截 | 测试 / lint / CI | ❌ 是"程序"，不是 spec | 硬（100% 确定） |

1. **第1层 · 上下文工程（这层才是 spec，软）**：别指望 AI "记得"，要让 spec **一直在它眼前**。
   - 全局铁律 → `alwaysApply` 的 Rule（每次自动注入）。
   - 功能 spec → 每步 `@` 引用或工具命令自动读取。
   - 原因:AI 只对**当前上下文窗口**里的内容负责,不在窗口里 = 等于不存在。
   - **但即使 spec 在上下文里，AI 仍可能不照做——这就是它"软"的根源。**

2. **第2层 · 人工卡点（不是 spec，是"人"）**：流程故意"一步一停"，`design` 要你 review、`tasks` 逐条验收。**审查时拿 spec 当客观标尺**——但执行约束的是**你这个人**，不是 spec 文档本身。

3. **第3层 · 机器拦截（不是 spec，是"程序"）**：和 AI 无关的确定性程序，骗不过去——
   - TypeScript 编译 + ESLint（拦类型错误 / `any`）
   - 单元测试 / E2E（把验收标准**翻译成测试**，红了就是没达标）
   - pre-commit hook（husky）/ CI（不过不让 commit / merge）
   - **注意：是"测试/lint"这个程序才硬；spec 还是软的。** 你得把 spec 里的条款**翻译**成测试或 lint 规则，那个**翻译产物**才长出牙齿，spec 自己一直只是"说要什么"。

> 🔑 一句话记牢：**spec 只待在第 1 层，永远是软的；第 2、3 层那些有牙齿的东西根本不是 spec，是外挂的人和程序。spec 的价值不在"强制"，而在"把要什么说清楚、可对齐、可追溯"。**
>
> 打比方：**spec** = 图纸上写"这面墙承重 500kg"（图纸拦不住偷工减料）；**测试/CI** = 真拿 500kg 去压的质检机器（压垮就亮红灯）。图纸只负责"说要什么"，质检机器才负责"硬卡住"。

---

> 完整的 spec-driven = **Workflow(流程)** 驱动,把 **Rule/AGENTS.md(持久约束)** + **功能级 Spec(本次图纸)** 一起喂进上下文,再用 **Prompt** 逐步推进。四者各司其职,缺一不可。

## 五、Spec vs Rule：配置与使用的真正区别（重点）

### 5.1 先回答那个最关键的疑问：为什么 rule 有固定规范，spec 没有？

> **是的，rule 确实有固定规范（`.cursor/rules/*.mdc` + frontmatter + `alwaysApply`），而 spec 没有任何固定格式（随便什么 markdown 都行）。这个"不对称"不是巧合，而是由"谁来加载"决定的：**

| | 谁负责把它喂进上下文 | 所以…… |
| :--- | :--- | :--- |
| **Rule** | **系统（Cursor）自动加载** | 系统要"认得"它，就**必须遵守固定格式/位置**，否则系统找不到 → **所以 rule 有规范** |
| **Spec** | **你手动 `@` 引用** | 是人来挑、人来喂，系统不需要"认得"它 → **怎么写、放哪儿都行 → 所以 spec 无规范** |

一句话:**"自动加载"是用"固定格式"换来的;"自由格式"是用"手动加载"换来的。** 你看穿的"还是有固定规范"——指的就是 rule 这条**自动通道**;spec 走的是**手动通道**,自然不需要规范。

### 5.2 Spec vs Rule 全维度对比

| 维度 | **Spec（规约）** | **Rule（规则）** |
| :--- | :--- | :--- |
| **固定格式** | ❌ 无,任意 markdown | ✅ 有,`.mdc` + frontmatter |
| **放哪儿** | 任意位置(如功能目录下) | 必须 `.cursor/rules/`(或根目录 `AGENTS.md`) |
| **谁加载进上下文** | **你手动 `@` 或叫 AI 读** | **Cursor 自动注入** |
| **何时生效** | 只在你引用它的那次对话 | `alwaysApply` 时每次都在;或命中 `globs` 时 |
| **作用范围** | 绑定**这一次任务** | 跨**所有任务**(或某类文件) |
| **生命周期** | 任务做完即归档 | 永久挂着 |
| **描述内容** | "要造什么 + 怎么验收"(产物) | "怎么写、不能干啥"(习惯/红线) |

> 划重点:**"作用范围"不是文件里写出来的,是"加载方式"决定的。** 自动注入 → 跨所有任务;手动引用 → 只这一次。

### 5.3 两个具体例子对照

**这是 Spec**(普通 md,放功能目录,用时 `@` 它):
```markdown
## 功能：文章详情接口
### 要造什么
GET /api/article/:id，返回文章详情，供详情页渲染。
### 验收标准
1. 返回 JSON 格式
2. 必须包含 title(string)、description(string) 字段
3. id 不存在时返回 404
```
→ 描述"这次要造的那个接口",造完验收过就归档。

**这是 Rule**(放 `.cursor/rules/api.mdc`,系统每次自动注入):
```mdc
---
description: 后端接口通用规范
alwaysApply: true
---
# 接口铁律（所有接口都遵守）
- 一律返回 JSON
- 错误统一用 { code, message } 结构
- 字段命名用小驼峰
```
→ 不针对任何具体接口,以后写**每个**接口都得遵守,永不归档。

### 5.4 配置/使用步骤对照

**用 Spec(手动通道):**
1. 在功能目录建一个普通 md(名字随意),写"要造什么 + 验收标准"。
2. 做这个任务时,在对话里 `@该文件` 把它带进上下文。
3. 让 AI 照着实现,你对着验收标准检查。
4. 任务完成 → 文件归档/删除,**下次任务不再带它**。

**用 Rule(自动通道):**
1. 在 `.cursor/rules/` 下建 `xxx.mdc`。
2. frontmatter 写 `alwaysApply: true`(或用 `globs` 限定文件范围)。
3. 写入通用约定。
4. 保存即生效 → **以后每次对话 Cursor 自动注入,什么都不用做**。

> 核心差异浓缩成一句:**Spec 是"用时手动端上桌、用完撤走"的一次性图纸;Rule 是"摆在桌上永远不收"的通用规矩。区别全在你怎么把它接进上下文,跟文件内容长相无关。**
