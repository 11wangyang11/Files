# 前端编译打包综合指南

> 本文档涵盖 TypeScript 编译、Babel 转换、模块系统、打包工具对比及优化策略，是一份面向现代前端工程化的完整参考。

---

## 一、概述：为什么需要编译打包？

你写的 TypeScript / ES6+ 代码最终需要运行在目标环境（浏览器、Node.js 等）。但不同环境有不同限制：

- 浏览器可能不支持最新的 JS 语法（如可选链 `?.`）
- Node.js 默认使用 CommonJS 模块系统，而前端常用 ESM
- 浏览器不认识 TypeScript 类型

**编译打包的作用**：
1. **编译**：将 TS / 新语法转换成目标环境支持的 JS（降级）
2. **打包**：将多个模块合并，优化加载性能（代码分割、Tree Shaking、压缩）

整体流程：

```
源代码 (TS/JSX)
    ↓
【编译阶段】tsc / Babel
    ├── 删除类型注解
    ├── 转换新语法（箭头函数、类等）
    ├── 注入 polyfill（新 API）
    └── 输出：ES5/ES6 + 模块格式（CJS/ESM）
    ↓
【打包阶段】Webpack / Metro / Rollup
    ├── 解析依赖图
    ├── Tree Shaking（删除无用代码）
    ├── 代码分割（动态 import）
    ├── 压缩混淆
    └── 输出：最终 bundle
```

## 二、TypeScript 编译配置（tsconfig.json）

### 2.1 核心选项：`target` 与 `module`

```json
{
  "compilerOptions": {
    "target": "ES2020",     // 编译后的 JS 语法版本
    "module": "ESNext"      // 编译后的模块系统
  }
}
```

| 选项 | 作用 | 示例差异 |
|------|------|----------|
| `target: ES5` | 降级到 ES5 | 箭头函数 → `function`，`const` → `var` |
| `target: ES2020` | 保留现代语法 | 箭头函数、`?.`、`??` 不变 |
| `module: CommonJS` | 使用 `require` / `module.exports` | Node.js 环境 |
| `module: ESNext` | 保留 `import` / `export` | 打包工具（Webpack）更友好 |

> **选择建议**：  
> - **Node.js 项目**：`target: ES2020, module: CommonJS`  
> - **前端项目（有打包工具）**：`target: ES2020, module: ESNext`，让 Webpack 等工具进一步优化。

### 2.2 `moduleResolution` — 模块查找算法

当你写 `import foo from 'bar'`，TypeScript 需要找到 `bar` 模块。两种模式：

| 模式 | 查找规则 | 适用场景 |
|------|----------|----------|
| `node` | 只看 `main` 字段 | 传统 Node.js |
| `bundler`（推荐） | 解析 `exports` 条件导出 | 前端项目 + Webpack/Vite |

```json
{
  "compilerOptions": {
    "moduleResolution": "bundler"   // TypeScript 5.0+
  }
}
```

### 2.3 `isolatedModules` — 单文件编译兼容性

当使用 Babel / Metro 等单文件编译器时，某些 TypeScript 特性（如 `const enum`）会失效。启用此选项后，TypeScript 会报错，强制你使用兼容写法。

```json
{
  "compilerOptions": {
    "isolatedModules": true
  }
}
```

**禁止的语法**：
- `const enum`
- 导出类型后直接在值位置使用（需改用 `import type`）

### 2.4 `esModuleInterop` — ESM / CJS 互操作

当 CommonJS 模块（`module.exports = {}`）被 ESM 导入时，默认行为不符合预期。启用后会生成辅助代码，使 `import _ from 'lodash'` 正常工作。

```json
{
  "compilerOptions": {
    "esModuleInterop": true,
    "allowSyntheticDefaultImports": true
  }
}
```

### 2.5 其他常用配置

| 配置 | 作用 |
|------|------|
| `declaration: true` | 生成 `.d.ts` 类型声明文件（供库发布） |
| `sourceMap: true` | 生成 `.map` 文件，便于调试 |
| `noUnusedLocals: true` | 检测未使用的局部变量 |
| `strict: true` | 启用所有严格类型检查 |
| `baseUrl` + `paths` | 路径别名，如 `@components/*` |

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  }
}
```

## 三、Babel 转换与 Polyfill

### 3.1 Babel 的作用

- 将新语法（箭头函数、类、可选链等）转换为旧语法
- 注入 polyfill，为旧环境提供新 API（如 `Array.from`、`Promise`）
- 删除 TypeScript 类型注解（需要 `@babel/preset-typescript`）

> Babel **不做类型检查**，只做代码转换。类型检查由 `tsc` 或 IDE 负责。

### 3.2 核心预设：`@babel/preset-env`

```json
{
  "presets": [
    ["@babel/preset-env", {
      "targets": "> 0.5%, last 2 versions",
      "useBuiltIns": "usage",
      "corejs": 3
    }]
  ]
}
```

#### `targets` — 目标环境
指定需要支持的浏览器或 Node.js 版本，Babel 只会转换这些环境不支持的语法。

```json
// 示例：支持市场份额 >0.5% 的浏览器
"targets": "> 0.5%, not dead"

// 或指定具体版本
"targets": { "chrome": 80, "ie": 11 }
```

#### `useBuiltIns` — Polyfill 注入策略

| 模式 | 行为 | 适用场景 |
|------|------|----------|
| `false`（默认）| 不注入 polyfill | 现代浏览器项目 |
| `"entry"` | 根据目标环境，替换手动导入的 `core-js` | 需要全量控制 |
| `"usage"`（推荐）| 按代码中实际使用的新 API 注入 | 最小化体积 |

示例（`"usage"` 模式）：
```js
// 源代码
const arr = Array.from([1, 2, 3]);
const p = Promise.resolve(42);

// Babel 输出（自动注入所需 polyfill）
import "core-js/es/array/from";
import "core-js/es/promise";
const arr = Array.from([1, 2, 3]);
const p = Promise.resolve(42);
```

### 3.3 `@babel/plugin-transform-runtime`

避免辅助代码（如 `classCallCheck`、`extends`）在每个文件中重复，统一从 `@babel/runtime` 引用，减小打包体积。

```json
{
  "plugins": [
    ["@babel/plugin-transform-runtime", {
      "corejs": 3   // 也支持 polyfill
    }]
  ]
}
```

### 3.4 与 TypeScript 配合

```json
{
  "presets": [
    "@babel/preset-typescript",   // 删除类型注解，不做类型检查
    "@babel/preset-env",
    "@babel/preset-react"
  ]
}
```

> 此时类型检查需要单独运行 `tsc --noEmit`。

## 四、模块系统与 package.json 字段

### 4.1 `main` / `module` / `exports`

| 字段 | 作用 | 使用者 |
|------|------|--------|
| `main` | CommonJS 入口，`require` 加载 | Node.js、旧打包工具 |
| `module` | ESM 入口，`import` 优先加载 | Webpack、Rollup 等 |
| `exports` | 条件导出（标准），优先级最高 | 支持新规范的 Node.js 和打包工具 |

```json
{
  "name": "my-lib",
  "main": "lib/index.js",
  "module": "es/index.js",
  "exports": {
    ".": {
      "import": "./es/index.js",
      "require": "./lib/index.js",
      "types": "./lib/index.d.ts"
    },
    "./utils": {
      "import": "./es/utils.js",
      "require": "./lib/utils.js"
    }
  }
}
```

**`exports` 的访问限制**：只有显式声明的子路径可以被外部导入，内部实现被隐藏。

### 4.2 `sideEffects` — 副作用标记

告诉打包工具哪些模块有副作用（不能随意删除）。正确配置可优化 Tree Shaking。

```json
{
  "sideEffects": false            // 全都没有副作用
}
// 或
{
  "sideEffects": ["*.css", "*.scss"]   // 只有样式文件有副作用
}
```

**副作用示例**：
```js
import './global.css';      // 有副作用（CSS 必须被注入）
import './polyfill';        // 有副作用（修改了全局对象）
export const add = (a,b)=>a+b;  // 无副作用
```

### 4.3 `types` — TypeScript 类型入口

```json
{
  "types": "lib/index.d.ts"
}
```

## 五、打包工具对比：Webpack vs Metro

| 特性 | Webpack | Metro |
|------|---------|-------|
| 主要用途 | Web 应用 | React Native 移动端 |
| 代码分割（动态 import） | ✅ 原生支持 | ❌ 不支持，生成单一 bundle |
| Tree Shaking | ✅ 强（ESM） | 有限（需要配置 `inlineRequires`） |
| 模块缓存 | ✅ 持久化缓存 | 无 |
| 配置复杂度 | 高 | 低 |

### 5.1 Metro 的静态分析限制

由于 Metro 主要处理 RN 环境，对 ESM tree-shaking 支持较弱。例如：

```ts
// 通过 getter 导出，Metro 无法分析哪些属性被使用
const CRN = {
  get PriceInfo() { return require('./PriceInfo').default; }
}
export default CRN;
```

这种模式会导致所有 getter 对应的模块都被打包。推荐使用直接导出。

### 5.2 Webpack 的代码分割示例

```js
// 动态导入
import('./HeavyComponent').then(module => {
  const Heavy = module.default;
});
```

配合 `optimization.splitChunks` 提取公共库和运行时。

## 六、优化策略（通用）

### 6.1 Tree Shaking

**条件**：
- 代码必须使用 ESM（`import`/`export`）
- 打包工具配置 `mode: 'production'` 和 `optimization.usedExports: true`
- 库的 `sideEffects` 正确标记

**无法 Tree Shake 的模式**：
- CommonJS（`require`）
- 默认导出对象（`export default { a, b }`）
- 动态引用（`require(variable)`）

### 6.2 代码分割（Code Splitting）

- **按路由分割**：`React.lazy(() => import('./Page'))`
- **提取第三方库**：`splitChunks.cacheGroups.vendor`
- **提取公共模块**：被多个入口引用的模块单独打包

### 6.3 压缩与混淆

Webpack production 模式下默认启用 Terser 插件：
- 删除空格、注释、无效代码
- 缩短变量名（混淆）
- 可配置移除 `console` 语句

### 6.4 包体积分析

```js
// webpack.config.js
const BundleAnalyzerPlugin = require('webpack-bundle-analyzer').BundleAnalyzerPlugin;
module.exports = {
  plugins: [new BundleAnalyzerPlugin()]
};
```

运行构建后自动打开可视化报告，找出体积大的模块。

## 七、常见问题调试

### 7.1 Polyfill 未生效

- 检查 `useBuiltIns` 配置
- 若为 `"entry"`，确认是否手动导入了 `core-js`
- 在浏览器控制台打印 `Array.from` 验证

### 7.2 Tree Shaking 未工作

- 确认代码使用 ESM
- 检查 `package.json` 的 `sideEffects` 是否为 `false` 或正确列出副作用文件
- 使用 `webpack-bundle-analyzer` 查看未摇掉的模块

### 7.3 模块导入报错（升级依赖后）

- 检查库是否新增了 `exports` 字段，只允许特定路径导入
- 改用库文档推荐的导入方式

### 7.4 Babel 编译时 `const enum` 报错

- 开启 `isolatedModules: true`，改用普通 `enum` 或常量对象

### 7.5 类型检查与编译分离的最佳实践

```json
{
  "scripts": {
    "dev": "concurrently \"tsc --watch --noEmit\" \"babel src --watch --out-dir dist\"",
    "build": "tsc --noEmit && babel src --out-dir dist"
  }
}
```

## 八、总结：概念关联

| 概念 | 解决的问题 | 常见错误 |
|------|-----------|----------|
| `target` | 编译后的语法版本 | 设太低导致代码臃肿 |
| `module` | 模块系统 | 搞混 CJS/ESM 导致导入报错 |
| `moduleResolution` | 模块查找规则 | 配置 `node` 但依赖了 `exports` |
| `isolatedModules` | 单文件编译器兼容 | 用了 `const enum` 导致 Babel 失败 |
| `useBuiltIns: "usage"` | 按需注入 polyfill | 手动导入过多 polyfill 导致体积大 |
| `sideEffects` | 帮助 Tree Shaking | 未标记 CSS 副作用，导致样式丢失 |
| `exports` | 限制模块暴露边界 | 升级后内部路径无法导入 |
